# Мобильный АРМ водителя

Общие правила для любого агента, работающего в этом репозитории (Claude Code, Codex).
Android-приложение для водителей автопарка + backend-шлюз между приложением и 1С:ERP заказчика.
Полный контракт обмена и примеры XML: architecture.md

## Границы проекта

Делаем **только** шлюз и Android-приложение. Не трогаем и не проектируем:

- **1С:ERP** — АРМ логиста/медика/механика, разнарядки, вся бизнес-логика диспетчеризации. Делают 2 разработчика заказчика.
- **Топливный сервис** — сбор данных о расходе. Делает Python-разработчик заказчика.

1С — единственный источник правды. Шлюз бизнес-данные не дублирует и не становится
источником истины. Допустим только технический delivery-cache в контейнерном volume:
FCM-токены устройств и последние XML разнарядок для доставки телефону после push.
Если задача требует изменений в 1С — это вопрос к их команде, а не повод городить логику у нас.

## Роль автора

Backend-разработчик (Go, интеграции, PostgreSQL). Android/Kotlin — впервые на этом проекте.
По Kotlin/Compose объясняй решения, а не только выдавай код; по backend — сразу к сути.
Архитектурные решения принимает автор, не агент. Крупные изменения — сначала план, потом код.

## Доменный словарь

Термины и XML-теги на русском — это норма, не переводить и не «чинить».

- **Разнарядка** — задание на день на один экипаж (машина + водитель). Одна машина = одна разнарядка.
- **Ездка** — один рейс «погрузка → разгрузка» внутри разнарядки. Обычно 2–8 за день.
- **Прицеп** — принадлежит **ездке**, а не машине: между рейсами прицеп может меняться.
- Не путать `Ознакомление`/`НачалоСмены` (прочитал маршрут vs физически начал смену) и
  `Разгрузился`/`ОкончаниеСмены` (конец ездки vs конец смены) — детали в разделе «Флоу» ниже.

### События и их уровни

Уровень определяет, заполняется ли `<Ездка>` в теле события.

| Событие | Уровень | `<Ездка>` |
|---|---|---|
| `Ознакомление` | разнарядка | нет |
| `НачалоСмены` | разнарядка | нет |
| `ПрибылНаПогрузку` | ездка | да |
| `ЗагрузилсяВПуть` | ездка | да |
| `ПрибылНаРазгрузку` | ездка | да |
| `Разгрузился` | ездка | да |
| `Срыв` | ездка | да (причина — в `<Комментарий>`) |
| `ОкончаниеСмены` | разнарядка | нет |

Событие `ПринялЗадание` из контракта **исключено** — не добавлять, цикл ездки начинается сразу с `ПрибылНаПогрузку`.
Возврат на базу между ездками событием **не отмечается** — считается арифметикой в 1С.

## Флоу приложения (экраны)

Один непрерывный сценарий на день, каждый шаг — кнопка, отправляющая соответствующее событие:

1. Push о разнарядке (может прийти накануне вечером) → экран разнарядки, кнопка **«Ознакомлен»**
2. Кнопка **«Начать смену»** → `НачалоСмены`
3. **Roadmap** — список ездок дня по порядку (сортировка по `<Порядок>`, не идентификация им), для активной ездки цикл кнопок:
   «Прибыл на погрузку» → «Загрузился, в пути» → «Прибыл на разгрузку» → «Разгрузился»;
   отдельно — **«Ездка сорвана»** с обязательным полем комментария (`Срыв`)
4. Кнопка **«Закончить смену»** → `ОкончаниеСмены` (отдельно от разгрузки последней ездки)

Каждая ездка в roadmap показывает прицеп, если он пришёл в `<Ездка>`. Отменённые ездки остаются
в списке с пометкой «снято» (см. инвариант 5), а не пропадают.

## Инварианты — нарушать нельзя

1. **GUID события генерируется на телефоне в момент события**, не на сервере при приёме.
   1С берёт время факта из события и дедуплицирует по GUID. Без клиентского GUID повторная
   офлайн-отправка перезапишет реальное время события временем повторной отправки → едут цифры
   в отчётах по простоям и расчёте смены.
2. **Ответ 1С на события — поштучный.** Из локальной очереди удалять только события с
   `принято="true"`. Чистка всей пачки по факту HTTP 200 = безвозвратная потеря отбитых событий.
3. **Ездка адресуется GUID'ом.** `<Порядок>` — только для сортировки в UI, никогда как идентификатор:
   диспетчер переигрывает разнарядку до 17:00, строки меняются местами.
4. **Разнарядка приходит целиком с `<Версия>`.** Версия ≤ сохранённой — игнорировать как устаревшее.
   Пустой список ездок — НЕ отмена, отмена только через `<Статус>Отменена</Статус>`.
5. **Отменённая ездка остаётся видимой** водителю с пометкой, не исчезает из списка.
6. **Неотправленные события видны в UI.** Залипшая очередь ломает утренний выпуск машины на линию,
   а не только отчётность.
7. **Разнарядка доступна с вечера предыдущего дня.** `Ознакомление` приходит накануне (push вечером),
   не прятать «завтрашнюю» разнарядку до наступления `<ДатаВыезда>`.

## Стек

- **Android**: Kotlin, Jetpack Compose, MVVM, Retrofit + OkHttp, Room (очередь событий), FCM.
  Стартуем от готового MVVM/Compose boilerplate (не с пустого MainActivity) — чистим demo-фичи,
  подключаем свой API поверх готовой обвязки Gradle/DI/сети.
- **Backend**: Go — основной stateless-шлюз. Python используется для локальных инструментов,
  моков и проверки стыковки XML-контракта, не как источник бизнес-данных.
- **Обмен с 1С**: XML поверх HTTPS, токен в заголовке `X-Auth-Token`
- Целевые устройства: Android 13+, 4 ГБ ОЗУ (лучше 6+), от 5000 мА·ч. Рекомендованы realme C71/Note 70,
  Tecno Spark 40C. **Не** Xiaomi/Redmi/POCO/Huawei/Honor — агрессивно режут фон без документированного API.

## Работа с XML от 1С

- Кодировка UTF-8 без BOM, `Content-Type: application/xml; charset=utf-8`. Даты — ISO-8601 со смещением
  с минутами (`+03:00`); встречался баг `+03:` — валить с явной ошибкой, не «чинить» молча.
- Опциональные поля, легально пустые: `<Заказчик/>`, `<ПричинаОтмены/>`, `<Комментарий/>`
- `<Прицеп>` — внутри `<Ездка>` (`<Идентификатор>` + `<ГосНомер>`), в `<Машина>` его нет.
- `<Адрес>` бывает и полным, и коротким («Окуни») — UI не должен ломаться ни на том, ни на другом.
- Плановые времена в тестовых данных нереалистичны (15 мин на 100 км) — не «исправлять» план под факт молча.

## Стиль

- Простой скучный код без лишних абстракций — проект передаётся штатной команде заказчика,
  снижение bus factor важнее элегантности.
- Ошибки интеграции — явные и логируемые, никаких «тихих» fallback'ов на дефолтные значения.
- Комментарии только там, где неочевидно «почему». Не описывать «что» — это видно из кода.

## Чего не делать

- **Не угадывать контракт.** Если поведение поля не описано здесь и не подтверждено в @docs/architecture.md —
  спросить автора, а не выбирать вариант «на свой вкус». Открытые вопросы перечислены в конце того документа.
- Не добавлять GPS-трекинг — из объёма исключён.
- Не реализовывать автосинхронизацию (WorkManager/ретраи) и передачу рейса другому водителю —
  это дополнительный этап, не текущий.
- Не хранить бизнес-истину в шлюзе, не изобретать локальную «правду» параллельно 1С.
  Технический delivery-cache нужен только для доставки на телефон и не заменяет 1С.
- Не выставлять 1С в интернет и не ходить в неё с телефона напрямую — только через шлюз.
- Не менять контракт обмена в одностороннем порядке — он согласован с 1С-командой.
