# Backend API

Шлюз разводит два формата:

- 1С ↔ gateway: XML по согласованному контракту.
- Android ↔ gateway: JSON, чтобы не тащить XML-парсинг в приложение.

Все запросы требуют:

```http
X-Auth-Token: <token>
```

Для XML: `Content-Type: application/xml; charset=utf-8`, UTF-8 без BOM.
Для JSON: `Content-Type: application/json; charset=utf-8`.

## Service

### `GET /healthz`

Liveness-check.

### `GET /readyz`

JSON-статус конфигурации:

```json
{
  "status": "ok",
  "one_c_configured": true,
  "fcm_configured": false
}
```

## 1C -> Gateway

### `POST /api/1c/assignments`

Принимает полный XML `Разнарядка`.

Шлюз:

- валидирует обязательные поля и даты;
- сохраняет исходный XML в технический delivery-cache;
- игнорирует устаревшую версию той же разнарядки;
- отправляет FCM push водителю, если зарегистрирован токен;
- ставит два отложенных напоминания (см. ниже) либо снимает их, если
  разнарядка пришла со `<Статус>Отменена</Статус>`.

Ответ:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<Результат статус="ok"></Результат>
```

### Push-уведомления водителю

1С присылает разнарядку один раз и больше шлюз не дёргает, поэтому расписание
напоминаний держит шлюз. Отсчёт идёт от момента приёма разнарядки, а не от
часов на стене: разнарядка, выпущенная не в 17:00, обрабатывается так же.

| Тип (`data.type`) | Когда |
|---|---|
| `assignment_new` | сразу при приёме разнарядки от 1С |
| `assignment_reminder_30` | через `ASSIGNMENT_REMINDER_FIRST_MINUTES` (30), если не принята |
| `assignment_reminder_10` | через `ASSIGNMENT_REMINDER_SECOND_MINUTES` (50), если не принята |
| `assignment_cancelled` | при приёме разнарядки со статусом «Отменена» |

Напоминания снимаются, когда через `POST /api/mobile/events` проходит принятое
1С событие `Ознакомление` по этой разнарядке. Сообщение содержит и `notification`,
и `data`: без `notification` Android не покажет уведомление, если приложение
выгружено, а разнарядка приходит именно на телефон в кармане.

Повторный приём той же разнарядки с новой версией перезапускает отсчёт —
изменённую разнарядку водитель должен посмотреть заново.

## Android -> Gateway

### `POST /api/mobile/devices`

Регистрирует FCM-токен устройства.

```json
{
  "driver_id": "3c9d1a55-77e2-4f0b-8a6c-1d2e3f405162",
  "device_id": "android-device-id",
  "fcm_token": "..."
}
```

Ответ:

```json
{"status":"ok"}
```

### `GET /api/mobile/assignments?driver_id=<guid>`

Возвращает разнарядки водителя за последние `ASSIGNMENT_LIST_WINDOW_HOURS`
часов (по умолчанию 48 — покрывает выдачу «с вечера» плюс весь день), свежие
первыми. За один день у водителя может быть больше одной разнарядки —
раньше ручка `assignments/current` отдавала только последнюю, и более ранняя
для того же дня становилась недоступна; список это исправляет.

```json
{
  "assignments": [
    { "id": "...", "version": 2, "number": "ПрТр-000413", "...": "..." },
    { "id": "...", "version": 1, "number": "ПрТр-000412", "...": "..." }
  ]
}
```

### `GET /api/mobile/assignments/{id}`

Возвращает разнарядку по GUID в JSON — точечный запрос, например чтобы
переоткрыть конкретную разнарядку из локальной истории на телефоне.

Дополнение 2026-10-14 одинаково для списка и одиночной разнарядки:

```json
{
  "shift_total": {
    "positions": {"items": [
      {"product_id": "guid", "name": "Плита ПК 60-15", "unit": "шт",
       "quantity": "12.000", "weight": "18.600", "volume": "7.200"}
    ]},
    "weight": "18.600", "volume": "7.200"
  },
  "trips": [{
    "cargo": {
      "positions": {"items": [
        {"product_id": "guid", "name": "Плита ПК 60-15", "unit": "шт",
         "quantity": "4.000", "weight": "6.200", "volume": "2.400"}
      ]},
      "weight": "6.200", "volume": "2.400"
    },
    "contacts": [{
      "purpose": "Разгрузка", "role": "Контактное лицо", "name": "Евгений Петров",
      "phones": [{"display": "8 (8332) 40-55-50", "number": "+78332405550"}]
    }]
  }]
}
```

Показаны только новые поля и итоги; остальные поля разнарядки/ездки сохраняются.
`shift_total` — готовый итог 1С без отменённых ездок. Никакой агрегации в шлюзе.
`cargo.positions` — позиции конкретной ездки. Все количества, веса (т) и объёмы
(м³) — строки из XML. Позиции с одинаковой номенклатурой и разными единицами
не объединяются. Старые `composition`, `quantity`, `unit` продолжают передаваться,
но устарели; `quantity` нельзя использовать как общее количество ездки.

У старого XML отсутствуют `shift_total` и `cargo.positions`. Явный `<Позиции/>`
передаётся как `"positions": {}` (пустой `items` опускается), это **не отсутствие
блока** и не повод брать старый состав. Пустой итог сохраняет `positions: {}` и
нулевые строковые `weight`/`volume`. Пустые списки `contacts`/`phones` опускаются,
Android использует пустые списки по умолчанию. Пустые `name`, `display`, `number`
внутри существующих контактов/телефонов сохраняются строками. Непустой `number`
готов для набора, `display` — только для отображения; пустой номер некликабелен.
Полный XML и правила расширения — в [architecture.md](../architecture.md).

### `GET /api/mobile/assignments/{id}/xml`

Диагностическая ручка: возвращает исходный XML разнарядки, который пришёл от
1С. Нужна для стыковки и сверки, Android в обычном сценарии использует
JSON-ручки.

### `POST /api/mobile/events`

Принимает события от телефона в JSON, валидирует инварианты контракта, собирает
XML `События` и форвардит пачку в 1С:

```http
POST ${ONE_C_BASE_URL}/prtr_driver/events
```

Запрос:

```json
{
  "events": [
    {
      "id": "b3e2648a-9f42-4c18-b994-b03f4a705977",
      "type": "ПрибылНаПогрузку",
      "driver_id": "3c9d1a55-77e2-4f0b-8a6c-1d2e3f405162",
      "assignment_id": "b1e4f207-9a3c-4d15-8e77-0c6b5a4d3e2f",
      "trip_id": "e5f6a7b8-1c2d-4e3f-9a0b-5c6d7e8f9a0b",
      "time": "2026-09-10T07:34:12+03:00",
      "comment": ""
    }
  ]
}
```

Ответ — JSON-проекция поштучного ответа 1С:

```json
{
  "status": "ok",
  "events": [
    {
      "id": "b3e2648a-9f42-4c18-b994-b03f4a705977",
      "accepted": true
    },
    {
      "id": "9a4b2d3f-5c8e-4b02-8d22-3f6e7d1b8c42",
      "accepted": false,
      "error": "Разгрузка без отметки прибытия на разгрузку",
      "code": "one_c_rejected"
    }
  ]
}
```

Телефон удаляет из локальной очереди только события с `accepted: true`. `code` у
отбитого события — не от 1С (та отдаёт только текст ошибки), а свой, всегда
`one_c_rejected`: водителю в приложении он показывается в скобках рядом с
текстом причины, чтобы при жалобе была зацепка короче, чем пересказ фразы 1С.

Если `ONE_C_BASE_URL` не задан или 1С недоступна, endpoint отвечает не-2xx JSON
ошибкой; телефон должен оставить события в локальной очереди.

Формат ошибки для Android:

```json
{
  "code": "validation_error",
  "error": "событие ...: для Срыв обязателен Комментарий"
}
```

### `GET /api/mobile/drivers/{id}`

ФИО водителя по GUID — для экрана настроек сразу после привязки телефона,
не дожидаясь разнарядки в окне выдачи. Справочника водителей у шлюза нет:
имя берётся из последней пришедшей от 1С разнарядки этого водителя за весь
срок хранения delivery-cache. Разнарядки, переданные другому водителю, не
учитываются — в них уже чужое ФИО.

```json
{"id": "1cb0cea4-e22b-45b6-b43b-8ce59aa77d30", "name": "Костенко Павел"}
```

`404` с `"code": "driver_unknown"` — от 1С не приходило ни одной разнарядки
этого водителя (новый водитель или опечатка в GUID).

### `POST /api/mobile/documents`

Фото этапа рейса (снимается только камерой приложения, не из галереи).
С 0.8.0 обязательные снимки на двух этапах: `ЗагрузилсяВПуть` — грузовик
сзади и сбоку; `Разгрузился` — грузовик сзади, сбоку и документ (листов
документа может быть несколько). Каждый снимок — отдельный запрос.
`multipart/form-data`:

- `photo_id` — GUID фото, генерируется на телефоне в момент съёмки.
  Обязателен: это тот же идентификатор, что уходит в 1С как `X-Photo-Id`
  (см. ниже) — телефон и 1С опознают повторную отправку по нему.
- `driver_id`, `trip_id` — обязательные текстовые поля.
- `assignment_id` — текстовое поле, необязательное.
- `event_id` — необязательное: GUID события этапа, к которому снимок
  (тот же, что `<Событие><Идентификатор>`). Только формат GUID, иначе `400`.
- `kind` — необязательное: что на снимке — `truck_rear`, `truck_side`,
  `document`. Только `[a-z_]`, иначе `400` (значение уходит в заголовок к 1С).
  Версии приложения до 0.8.0 не шлют ни `event_id`, ни `kind`.
- `photo` — файл, JPEG или PNG.

Шлюз сохраняет фото в технический delivery-cache (`DATA_DIR/documents`)
и **синхронно пересылает в 1С**, отдельным запросом от `<Событие>`
(контракт согласован с их командой 2026-09-21):

```http
POST ${ONE_C_BASE_URL}/prtr_driver/photo
Content-Type: image/jpeg | image/png
X-Photo-Id: <тот же GUID, что photo_id>
X-Assignment-Id: <assignment_id>
X-Trip-Id: <trip_id>
X-Event-Id: <event_id>      (только если пришёл от телефона)
X-Photo-Kind: <kind>        (только если пришёл от телефона)
```

`X-Event-Id` и `X-Photo-Kind` согласованы с 1С 2026-10-28 (architecture.md
§14 п.8). 1С определяет этап по типу события из `X-Event-Id` и досчитывает
его, если событие придёт позже фото. Ключ хранения — `X-Photo-Id`: новые
фото по ездке предыдущие не перезаписывают, повтор того же `X-Photo-Id`
подтверждается без дубля. Фото без новых заголовков (версии приложения
до 0.8.0) принимаются как раньше.

Тело — бинарное содержимое файла как есть, без base64 и без
multipart-обёртки. Ответ 1С:

```xml
<Результат статус="ok" ид="<X-Photo-Id>"/>
```

Ответ телефону:

```json
{"status": "ok", "id": "<photo_id>"}
```

Если `ONE_C_BASE_URL` не настроен или 1С недоступна/отклонила фото —
`503`/`502` с JSON-ошибкой, телефон должен оставить фото в локальной
очереди на повтор (тот же принцип, что у `/api/mobile/events`). Локальная
копия в delivery-cache сохраняется в любом случае — даже если 1С сейчас
недоступна, повторно посылать файл не придётся, шлюз пересошлёт его сам
при следующей попытке телефона с тем же `photo_id`.

При успешной доставке в 1С шлюз проставляет `DeliveredAt` — с этого
момента действует короткий срок хранения. Пока не доставлено —
`DOCUMENT_PENDING_RETENTION_DAYS` (по умолчанию 90), после подтверждения
— `DOCUMENT_DELIVERED_RETENTION_DAYS` (по умолчанию 7). Чистка раз в
сутки в фоне.

Координаты места съёмки 1С предлагала передавать опционально
(`X-Latitude`/`X-Longitude`) — отказались: GPS-трекинг сознательно
исключён из объёма проекта (см. AGENTS.md).
